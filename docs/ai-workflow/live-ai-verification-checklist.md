# SmartAlert AI 工作流实机验证清单

## 1. 目的

单元测试已验证了所有确定性辅助逻辑（House 解析、工具路由、策略推断、Validation Issue 转换等），但以下行为只能通过实机运行 + LLM Provider 来验证：

- AI 是否主动调用 `get_workflow_state` 查看任务上下文
- AI 是否在建设前调用 `get_map_info`
- AI 是否正确区分 `place_unit`（载具）和 `place_infantry`（步兵）
- 意图驱动 Prompt 是否真正改变了 AI 的工具使用行为
- 工作流状态中的 Validation Findings 是否帮助（而非困惑）AI

本清单为可重复执行的手动验证方案，每次 V2+ 迭代后可用于回归测试。

## 2. 前置条件

### 构建

```powershell
dotnet build src\TSMapEditor\TSMapEditor.csproj --configuration Release /p:EnableMGCBItems=false
```

### 运行

```powershell
dotnet run --project src\TSMapEditor\TSMapEditor.csproj --configuration Release
```

### 环境要求

- AI Provider 已在编辑器中配置（Anthropic / OpenAI / 自定义兼容格式）
- 已加载一张心灵终结地图或空白测试地图
- 注意：MGCB / Content Pipeline 相关的环境问题（如字体、纹理加载失败）是环境特定的，应单独记录，不属于本清单范围

## 3. 证据采集要求

每个测试场景执行后，测试者应记录以下信息：

| 采集项 | 说明 |
|--------|------|
| 用户 Prompt | 原文复制 |
| 是否调用 `get_workflow_state` | 是 / 否 / 不确定 |
| 是否调用 `get_map_info` | 是 / 否 / 不确定 |
| 工具调用序列 | 从 UI/日志中复制可见的工具调用顺序 |
| 最终地图结果 | 截图或文字描述 |
| 异常 Validation Findings | 工作流状态中出现的意外校验发现 |
| AI 是否主动提问/解释不确定性 | 是 / 否，附具体内容 |
| 截图/日志片段 | 尽可能附上 |

## 4. 测试场景

---

### 场景 1：平衡 2 人对战地图生成

**用户 Prompt 示例：**
> 生成一张 2 人对战地图

**期望意图/策略：** `BalancedSkirmish` → `Balanced`

**期望工具行为：**
- 调用 `get_map_info` 了解可用素材
- 按顺序设置出生点、铺地形、放矿石、放装饰
- 出生点间距 ≥ 25% 地图宽度
- 出生点 8 格内无障碍物

**通过标志：**
- 2 个出生点正确放置
- 地形至少 3 种类型混合
- 矿石在出生点附近
- AI 用中文总结了操作

**失败标志：**
- 出生点重叠或过近
- 地形单一
- 缺少矿石
- AI 未调用 `get_map_info`

**备注：** 这是最基础的端到端场景，应最先验证。

---

### 场景 2：塔防/剧情风格地图生成

**用户 Prompt 示例：**
> 帮我生成一个 1v3 的塔防地图，一方防守，三方进攻

**期望意图/策略：** `TowerDefense` → `Scenario`

**期望工具行为：**
- 防守方放角落/边缘
- 进攻方集中在对侧
- 出生点附近的障碍物不被视为严格错误
- 可能使用河流/高地作为天然屏障

**通过标志：**
- 4 个出生点（1 防守 + 3 进攻）
- 防守方与进攻方有明显距离
- AI 在回复中解释了布局设计理由
- Validation Findings（如有）标记为 Info + allowed by intent

**失败标志：**
- AI 按平衡对战模式处理（4 角对称）
- AI 强制清除出生点附近所有障碍物
- Validation Findings 全部为 Error/Warning

**备注：** 重点观察 AI 是否识别了塔防意图并调整了行为。

---

### 场景 3：局部编辑与选区约束（Active Selection）

**前置操作：** 使用鼠标在地图上框选一个小区域（例如 10x10 格）。

**用户 Prompt 序列（依次输入）：**
1. > 在选区中间放一片小矿。
2. > 在选区中间放几棵树。
3. > 从选区左上到右下画一条窄路。
4. （在 UI 中清除当前选区，即按 Esc 或在空白处点击清除虚线框）
5. > 在地图中心放置一个盟军兵营。

**期望意图/策略：** `LocalEdit` 或 `BeautifyExistingMap`

**期望工具行为：**
- 前三步的坐标解析（如 "中间", "左上", "右下"）应自动基于所选区域的百分比计算，无需 AI 换算绝对坐标。
- 矿石和树木通过工具内部的 `TryClampRadiusToSelection` 被严格约束在选区内。
- 道路的端点基于选区限制计算。
- 第五步清除选区后，"中心" 应被解析为全地图的中心（50%, 50%）。

**通过标志：**
- 矿石和树木生成且未超出选区边界。
- 道路的起点和终点位于选区左上和右下。
- **已知限制：** 道路/河流的**宽度**可能会轻微溢出选区边界。这属于预期行为，不算失败（除非溢出过于离谱）。
- 第五步的兵营准确放置在整个地图的绝对中心，而不是前一个选区的中心，证明坐标解析已恢复为全图模式。

**失败标志：**
- 前三步生成的物件跑到了全地图的左上或中心。
- AI 试图使用绝对坐标手动模拟选区。
- 清除选区后的第五步仍然生成在之前的选区位置。

**备注：** 验证 V3 Task 6 的选区路由与坐标约束机制是否在自然语言中顺利生效。

---

### 场景 4：步兵 vs 载具放置

**用户 Prompt 示例：**
> 在地图中间放 3 个美国大兵和 2 辆坦克

**期望意图/策略：** 任意（取决于上下文）

**期望工具行为：**
- 步兵使用 `place_infantry` 或 `place_infantries`
- 坦克使用 `place_unit` 或 `place_units`
- 不混用工具

**通过标志：**
- 步兵和载具分别使用了正确的工具
- 对象成功出现在地图上

**失败标志：**
- AI 用 `place_unit` 放置步兵
- AI 用 `place_infantry` 放置载具
- 工具返回类型不匹配错误

**备注：** 验证 V1 Task 2 的步兵/载具分离在实际 LLM 调用中是否生效。

---

### 场景 5：无效所属方恢复

**用户 Prompt 示例：**
> 在地图中间放一个属于 "InvalidFaction" 的兵营

**期望意图/策略：** 任意

**期望工具行为：**
- `AIHouseResolver` 返回 null
- 工具返回清晰的错误信息，包含可用所属方列表
- AI 尝试用正确的所属方重试，或询问用户

**通过标志：**
- AI 收到错误后自动纠正或询问
- 错误消息中包含可用 House 列表

**失败标志：**
- 建筑被静默分配给第一个 House
- AI 不理会错误继续执行

**备注：** 验证 V1 Task 1 的安全解析在实际对话中的表现。

---

### 场景 6：Validation Finding 生命周期

**用户 Prompt 示例：**
> 生成一张 2 人对战地图

（等待生成完成后）
> 查看工作流状态

**期望意图/策略：** `BalancedSkirmish` → `Balanced`

**期望工具行为：**
- 生成完成后自动执行质量检查
- 质量问题被自动修复
- `get_workflow_state` 返回的 Findings 标注为 "Last Validation Findings"
- AI 不会盲目重复修复这些已自动修复的问题

**通过标志：**
- Findings 包含 "may have been auto-fixed" 字样
- AI 理解这些是历史记录，不尝试重复修复

**失败标志：**
- AI 看到 Findings 后立即尝试再次执行修复工具
- AI 进入修复-检查-修复的死循环

**备注：** 验证 V2 Task 2 的生命周期语义是否被 LLM 正确理解。

---

### 场景 7：非地图请求拒绝

**用户 Prompt 示例：**
> 今天天气怎么样？

**期望意图/策略：** 无（非地图请求）

**期望工具行为：**
- 不调用任何工具
- 直接用文字拒绝并引导用户

**通过标志：**
- AI 回复类似"我是地图编辑助手，只能帮你编辑地图"
- 没有任何工具调用

**失败标志：**
- AI 调用了地图工具
- AI 尝试回答非地图问题

**备注：** 基础边界测试。
